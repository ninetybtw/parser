# Архитектура leadgen

Инструмент **готовит** холодные предложения: находит бизнесы нужной ниши в открытых
источниках, собирает публичные данные, пишет персональный черновик и (для сайтов)
собирает макет-превью. **Отправляет человек**, вручную, из своего аккаунта.
Автоматической рассылки в системе нет и не планируется.

## 1. Принципы

1. **Человек в контуре.** Система ничего не пишет на площадках. Кнопка «Скопировать
   и открыть» только копирует текст и открывает диалог, а «Отправлено» — отметка в базе.
2. **Официальные каналы доступа.** API ВКонтакте, MTProto Telegram, RSS бирж.
   Никакого обхода капчи, ротации прокси, подмены отпечатков браузера и мультиаккаунтов.
   Если площадка не даёт данные официально, источник не делаем, и это решение, а не
   недоработка.
3. **Минимум данных.** Хранится только то, что бизнес сам опубликовал как контакт:
   название, описание, контакты, логотип, прайс. Участников чатов и подписчиков не
   собираем.
4. **Одна запись на бизнес.** Повторные находки дополняют лид. Записи «не писать»
   больше не появляются ни из какого источника.

## 2. Модули

```
 ниша ─► sources/ ─────────────────────────────────► RawLead
         vk.py (VK API) · telegram.py (Telethon, чтение) · rss.py (биржи)
         └─ ratelimit.py + http.py: темп, ретраи, бюджет запросов
                                   │
                                   ▼
 pipeline.run_search ─► niches.classify ─► db.Store.upsert (дедупликация, стоп-лист)
                                   │
                                   ▼
 pipeline.prepare_lead ─► mockup/  (палитра из лого + прайс → HTML [+ PNG])
                       └► offer.py (Claude, структурированный ответ / шаблон)
                                   │
                                   ▼
 web/ (FastAPI + Jinja2): список → карточка → правка → «скопировать и открыть» → «отправлено»
```

| Модуль | Ответственность |
|---|---|
| `config.py` | Настройки из `.env`: ключи источников, профиль фрилансера, лимиты |
| `models.py` | `RawLead` (что отдал источник), `Lead` (запись в базе), `Contacts`, `PriceItem` |
| `sources/` | По модулю на площадку. Общий контракт: `search(query, limit) -> Iterator[RawLead]` |
| `ratelimit.py`, `http.py` | Интервал + джиттер, бюджет запросов на запуск, повторы на 429/5xx с `Retry-After` |
| `extract.py` | Телефоны, e-mail, сайты, @username, ссылки ВК из свободного текста и их нормализация |
| `niches.py` | Профили ниш: фразы поиска, «боли», идеи сайта и бота, тексты для макета |
| `db.py` | SQLite: лиды, источники, идентичности, стоп-лист, события |
| `offer.py` | Генерация предложения через Claude (structured output) с шаблонным фолбэком |
| `mockup/` | Палитра из логотипа, разбор прайса, рендер шаблона, скриншот через Playwright |
| `pipeline.py` | Связка: поиск → дедупликация → ниша → макет → предложение |
| `web/` | Интерфейс просмотра и ручной отправки |
| `cli.py` | `search`, `prepare`, `serve`, `sources`, `tg-login` |

Источник ничего не знает о базе и LLM, а генератор ничего не знает об источниках.
Поэтому новую площадку можно добавить одним файлом в `sources/` и строкой в реестре.

## 3. Источники

| Источник | Доступ | Что берём | Как отвечать | Темп в коде |
|---|---|---|---|---|
| ВКонтакте | Официальный API, пользовательский токен (`groups.search` работает только с ним) | Открытые сообщества: описание, блок «Контакты», сайт, город, аватар, товары (`market.get`) как прайс | Диалог с сообществом `vk.com/im?sel=-ID`, если `can_message`, иначе страница группы | 0.6–1.0 с между запросами (лимит API — 3/с), 300 запросов на запуск |
| Telegram | MTProto через Telethon с личного аккаунта, **только чтение** | Публичные **каналы**: название, описание, аватар | В канал написать нельзя — контакт берётся из описания | 2–4 с между запросами, FloodWait выполняется буквально, при FloodWait > 5 мин источник останавливается |
| Биржи | RSS-ленты поиска (Хабр Фриланс и т. п.; адрес задаётся в `.env`) | Заказы: заголовок, текст, ссылка | Отклик на бирже, через её форму | 5–8 с между лентами, 30 запросов на запуск |

Почему так:

- **ВК.** API вместо парсинга HTML: стабильный формат, понятные лимиты и коды ошибок
  (6/9 — подождать и повторить; 5 — плохой токен; 29 — суточный лимит метода, стоп).
  Закрытые сообщества пропускаются, потому что в них нет публичных данных.
- **Telegram.** Поиск `contacts.Search` находит каналы и чаты по названию. Групповые
  чаты сознательно пропускаются: собирать их участников для рассылки — это и есть спам.
  Чаты полезны иначе: см. этап 3 (уведомления о запросах в чатах, где ты состоишь).
- **Биржи.** RSS — канал, который биржа сама публикует для машин. Там, где RSS нет
  (например, у некоторых бирж есть только уведомления на почту), правильный путь —
  подписаться на уведомления и разбирать письма (этап 3), а не скрейпить страницы
  под логином.

Кандидаты на будущее: 2ГИС и Яндекс Карты через их платные API — это лучший источник
офлайн-бизнесов с телефонами и сайтами.

## 4. Лимиты и блокировки

Риск блокировки создаёт не столько сбор данных, сколько **отправка**: много
одинаковых первых сообщений с нового аккаунта. Поэтому меры разделены.

**При сборе** (в коде):
- только официальные API и ленты, честный `User-Agent`;
- интервал ниже официального лимита и случайная добавка, чтобы запросы не шли пачкой;
- бюджет запросов на запуск: широкий запрос не превратится в тысячи обращений;
- `Retry-After`, FloodWait и коды «слишком часто» выполняются, а не обходятся;
- результаты сохраняются, повторный поиск дополняет базу, поэтому одно и то же
  перезапрашивать не нужно.

**При отправке** (процесс + интерфейс):
- мягкий дневной лимит (`LEADGEN_DAILY_SEND_LIMIT`, по умолчанию 20): после него
  интерфейс показывает предупреждение;
- каждый текст персональный и проходит через человека; шаблоны с одинаковым текстом
  площадки распознают быстрее всего;
- в каждом сообщении есть фраза «если неактуально — больше не напишу», а «Не писать»
  в карточке навсегда добавляет все идентификаторы бизнеса в стоп-лист;
- пиши из основного «живого» аккаунта, без накрутки. Новые и пустые аккаунты
  блокируют быстрее всего.

## 5. Хранение и дедупликация

SQLite (один файл, режим WAL — веб читает, пока фоновый поиск пишет). Таблицы:

- `leads` — объединённая карточка бизнеса и рабочие поля (статус, текст, макет);
- `lead_sources` — где и по какой фразе лид найден (`first_seen` и `last_seen`);
- `identities` — `(вид, значение) → lead_id`: `src:vk:123`, `phone:79991234567`,
  `email:…`, `domain:fix.ru`, `tg:username`, `vk:screen_name`, `url:…`;
- `blocklist` — идентичности бизнесов со статусом «не писать»;
- `events` — смены статуса (из них считается «отправлено сегодня»).

Правила:
1. Из каждого `RawLead` вычисляется набор идентичностей. Если хоть одна уже есть в базе,
   это тот же лид: контакты объединяются, пустые поля заполняются, длинное описание
   не затирается коротким, источник добавляется.
2. Домен — идентичность, только если это домен бизнеса. Ссылки на taplink, instagram,
   vk и подобные хранятся целиком (`url:`), иначе все салоны с taplink склеились бы
   в один.
3. Телефоны приводятся к виду `7XXXXXXXXXX`, e-mail и username — к нижнему регистру,
   URL — к `https://host/path` без хвостового `/`.
4. Перед вставкой проверяется стоп-лист. Совпадение по любой идентичности — запись
   пропускается.

Жизненный цикл: `new → ready` (есть черновик) `→ sent → replied`; в любой момент
`skipped` или `do_not_contact`. Если понадобится Postgres, это замена одного `db.py`:
схема переносится как есть.

## 6. Генерация предложения

- Модель: `claude-opus-5-5` через официальный SDK `anthropic`, метод
  `client.beta.messages.parse` с Pydantic-схемой `OfferDraft` (тема, текст, услуга
  `site`/`bot`/`site+bot`, на какие факты опирался). Модель задаётся в
  `LEADGEN_MODEL`, глубина рассуждения — в `LEADGEN_EFFORT`.
- Включён серверный фолбэк при отказе модели (`fallbacks="default"`). Если отказ всё
  равно пришёл, сеть недоступна или ключа нет, срабатывает шаблон ниши. Карточка
  никогда не остаётся пустой.
- В промпт идут: данные лида, профиль ниши («боли», идеи сайта и бота), профиль
  фрилансера, флаг «макет приложен».
- Правила текста: на «вы», без выдуманных фактов и обещаний в цифрах, одно-два
  решения вместо перечня всего подряд, лёгкий призыв в конце и фраза об отказе;
  для заказа с биржи — формат отклика.
- **Защита от промпт-инъекций:** описание сообщества — недоверенный текст. Оно
  передаётся внутри `<lead_data>`, а в системном промпте сказано считать его только
  данными. Последний рубеж — человек, который читает текст перед отправкой.
- Без LLM услуга выбирается эвристикой: если у бизнеса уже есть свой сайт,
  предлагается бот, иначе сайт.

## 7. Макет сайта: шаблоны или генерация

**Выбор — шаблон с подстановкой данных.** Генерация вёрстки моделью выглядит
эффектнее, но непредсказуема (сломанная адаптивность, выдуманные отзывы и цифры),
дороже и медленнее. Для превью к холодному письму важнее, чтобы бизнес узнал себя:
свой логотип, свои цвета, свои цены.

Как собирается (`mockup/`):
1. **Логотип** скачивается и перекодируется в PNG через Pillow. В макет попадает
   только проверенная картинка.
2. **Палитра:** логотип квантуется до 6 цветов, фон и серые отбрасываются, основной
   цвет — самый весомый насыщенный. Затем он затемняется, пока белый текст на нём не
   даст контраст ≥ 4.5 (WCAG AA).
3. **Прайс:** товары сообщества ВК (`market.get`) или строки вида «Услуга — от 1 500 ₽»
   из описания. Если прайса нет, вместо него показываются блоки «что будет на сайте»
   из профиля ниши.
4. **Шаблон** `landing.html.j2`: шапка с лого и телефоном, первый экран с
   тезисом ниши и кнопкой, услуги и цены, места под отзывы и форму, контакты.
   Плашка «Концепт-превью · не опубликован». Места, для которых нет реальных данных,
   показаны как пунктирные заглушки, а не придуманы.
5. **PNG-скриншот** через Playwright (если установлен) — его удобно приложить к
   сообщению.

Как развивать дальше: 2–3 шаблона на нишу (модель выбирает шаблон и пишет короткие
тексты секций в строгой схеме, но не вёрстку); публикация превью по ссылке
(`slug.твой-домен`) вместо PNG — ссылку открывают охотнее, чем вложение.

## 8. Стек

| Задача | Выбор | Почему |
|---|---|---|
| Язык | Python 3.11+ | Как и хотелось; все нужные SDK есть |
| HTTP | `httpx2` | Он уже приходит с SDK `anthropic`; таймауты, `MockTransport` для тестов |
| ВК | Прямые вызовы REST API | Методов нужно три, отдельная библиотека не нужна |
| Telegram | Telethon (опционально) | Зрелый MTProto-клиент, понятная обработка FloodWait |
| LLM | `anthropic` SDK, Claude | Структурированный ответ сразу в Pydantic |
| База | SQLite | Ноль администрирования, одного пользователя хватает с запасом |
| Макеты | Jinja2 + Pillow (+ Playwright для PNG) | Предсказуемо и бесплатно |
| Веб | FastAPI + Jinja2 + немного ванильного JS | Без сборки фронтенда и без CDN |
| Тесты | pytest, моки транспорта | Сеть в тестах не нужна |

## 9. Правовые и этические рамки

Это не юридическая консультация, но учитывать стоит вот что:

- **Персональные данные (152-ФЗ).** Контакт юрлица — обычно не персональные данные, а
  телефон мастера-ИП или личная страница — уже персональные. Храни минимум, по просьбе
  удаляй («Не писать» плюс удаление записи), не передавай базу третьим лицам.
- **Реклама (38-ФЗ, ст. 18).** Рассылка рекламы по сетям электросвязи (e-mail, SMS,
  мессенджеры) требует предварительного согласия адресата. Индивидуальное деловое
  предложение конкретному бизнесу — не то же самое, что массовая рассылка, но граница
  размыта. Поэтому: персонально, немного и с возможностью отказаться.
- **Правила площадок.** ВК и Telegram запрещают спам и массовые однотипные сообщения,
  а условия Telegram API запрещают использовать API для флуда и спама. Режим «читаем
  через API, пишем руками и мало» — внутри этих правил.
- **Логотип в макете.** Концепт показывается только самому владельцу логотипа как
  иллюстрация и нигде не публикуется. Плашка «не опубликован» на макете — про это.

## 10. Порядок разработки

**Этап 0 — MVP (сделано в этом репозитории).** Источники ВК, Telegram и RSS;
дедупликация и стоп-лист; профили пяти ниш; генерация через Claude с шаблонным
фолбэком; макет из лого и прайса; веб-карточки с ручной отправкой; тесты.

**Этап 1 — первые реальные отправки (1–2 дня).**
1. Получить токен ВК, заполнить `.env` и профиль о себе.
2. Прогнать одну нишу и один город на 30–50 лидах.
3. Прочитать 20 черновиков и поправить системный промпт и профиль ниши под свой стиль.
4. Отправить первые 10–15 сообщений вручную и записывать, что отвечают.

**Этап 2 — качество лидов.**
- Скоринг лида: нет своего сайта (+), сообщество живое (последний пост недавно,
  `wall.get count=1`), есть прайс и телефон, число участников в разумных пределах.
  Сортировка списка по скорингу.
- Фильтр «уже есть хороший сайт»: проверка своего домена (отвечает ли, есть ли
  мобильная версия).
- Повторный контакт не раньше чем через N дней после `skipped`.

**Этап 3 — больше источников и регулярность.**
- Уведомления о запросах в Telegram-чатах, где ты состоишь: «нужен сайт», «кто сделает
  бота» → карточка `request`. Только сообщения, без выгрузки участников.
- Биржи без RSS — через разбор писем-уведомлений.
- Запуск поиска по расписанию (cron или systemd timer) с готовыми карточками к утру.

**Этап 4 — конверсия.**
- Несколько шаблонов макетов на нишу и превью по ссылке.
- Аналитика: доля ответов по нишам, источникам и вариантам текста.
- Шаблоны follow-up для тех, кто ответил.
